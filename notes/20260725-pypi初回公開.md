# PyPI 初回公開 (0.15.3.0)

`openmc-anywhere` 0.15.3.0 was published to PyPI on 2026-07-25, so `pip install openmc-anywhere` finally does what the README has been claiming; the GitHub Pages simple index stays as a second channel but is no longer the only one.
Five wheels went up in one shot — `manylinux_2_28` for x86_64 and aarch64, `macosx_11_0` for x86_64 and arm64, and `win_amd64` — and installing from PyPI into a clean venv gives `openmc.__version__ == "0.15.3.0"` with DAGMC support compiled in and a working `njoy` on PATH.
The upload used an account-scoped API token via `uv publish`; `uv` does not read `~/.pypirc`, so the token was passed through `UV_PUBLISH_TOKEN` from a file under the gitignored `out/`.

The version scheme changed for this release from `0.15.3.post214` to `0.15.3.0`, meaning upstream release plus this repository's own build revision.
The commit distance 214 was deliberately dropped because it moves with every submodule bump, which makes it worthless as something a user can pin against, and because PEP 440 forbids a second post segment — there was simply no next number available for rebuilding the same upstream pin.
That mattered immediately: PyPI never lets a filename be reused even after deletion, and it rejects local version identifiers, so any rebuild needs a genuinely new number.
The exact upstream revision now lives in the README table and in `thirdparty-license/README.md` rather than in the version string, and the compiled binary still reports it — `openmc --version` prints `0.15.4-dev214` with commit `54b661d39`, which is what upstream's own setuptools-scm defaults would have produced.

Publication was gated on third-party license work, because a wheel that statically links MOAB carries LGPL-3.0 obligations that a deleted release cannot retroactively fix.
`thirdparty-license/` now holds the license text of every redistributed component plus the GPL-3.0 text that LGPL-3.0 §4(b) requires alongside it, PEP 639 `license-files` ships the whole directory inside every wheel under `dist-info/licenses/`, and a single `NOTICE` file feeds the PyPI page, the Pages index and the GitHub Release body so that GPL-3.0 §6(d) directions sit next to the object code at all three distribution points.

Four compliance gaps remain and each needs a rebuild, so they will land as 0.15.3.1.
The sharpest is LGPL-3.0 §4(c): `openmc` prints a copyright banner at startup and MOAB's copyright is absent from it, which no amount of shipped files can fix and which switching MOAB to a shared library would not fix either, since §4(a)–(c) apply to any Combined Work regardless of linkage.
The others are the bundled `libgomp` in the linux wheels needing a GCC source offer under GPL-3.0 §6, the vendored `fmt` and `pugixml` needing their MIT notices, and the mingw-w64 runtime statically linked into the Windows wheel.
Separately, the account-scoped token should be replaced by a project-scoped one now that the project exists, and the release should move to PyPI Trusted Publishing so that no token is stored at all.

2026-07-25 に `openmc-anywhere` 0.15.3.0 を PyPI へ公開した。README がずっと案内していた `pip install openmc-anywhere` がようやく実際に動く。GitHub Pages の simple index は第二の経路として残るが、唯一の経路ではなくなった。
wheel は一度に5つ — x86_64 と aarch64 の `manylinux_2_28`、x86_64 と arm64 の `macosx_11_0`、そして `win_amd64`。PyPI から新しい venv に入れると `openmc.__version__` は `0.15.3.0` を返し、DAGMC 有効でビルドされており、`njoy` も PATH 上で動く。
アップロードはアカウントスコープの API トークンを `uv publish` に渡して行った。`uv` は `~/.pypirc` を読まないので、gitignore 済みの `out/` 配下のファイルから `UV_PUBLISH_TOKEN` 経由で渡している。

版番号はこのリリースから `0.15.3.post214` を捨て、上流リリース + このリポジトリ独自のビルド版数を意味する `0.15.3.0` にした。
コミット距離 214 を意図的に外したのは、submodule を進めるたびに動く値で利用者が固定する対象として使い物にならないからであり、また PEP 440 が post セグメントの二重付与を許さないため、同じ上流 pin で作り直すときの採番先が存在しなかったからでもある。
これは即座に効いてくる問題だった。PyPI は削除後もファイル名の再利用を永久に拒否し、local version identifier も受け付けないので、作り直しには本当に新しい番号が要る。
正確な上流リビジョンは版文字列ではなく README の表と `thirdparty-license/README.md` に置いた。バイナリ自身も申告しており、`openmc --version` は `0.15.4-dev214` とコミット `54b661d39` を表示する — これは上流の setuptools-scm の既定が生成したはずの値そのものである。

公開はサードパーティライセンスの整備待ちだった。MOAB を静的リンクした wheel は LGPL-3.0 の義務を伴い、Release を消しても遡って直せないからである。
`thirdparty-license/` に再配布する全部品のライセンス全文と、LGPL-3.0 §4(b) が併せて要求する GPL-3.0 本文を置いた。PEP 639 の `license-files` がディレクトリごと全 wheel の `dist-info/licenses/` へ入れ、単一の `NOTICE` が PyPI ページ・Pages の index・GitHub Release 本文の3面に供給されるので、GPL-3.0 §6(d) の「ソースの在処」が object code の隣に揃う。

未解消の告知不備が4件あり、いずれも作り直しを伴うので 0.15.3.1 で対応する。
最も鋭いのは LGPL-3.0 §4(c) で、`openmc` は起動時に著作権バナーを表示するのに MOAB の著作権表示がそこに無い。これはファイルを同梱しても直らず、MOAB を共有ライブラリ化しても直らない — §4(a)〜(c) はリンク形態を問わず Combined Work に等しくかかるからである。
残りは linux wheel が同梱する `libgomp` に GPL-3.0 §6 のソース入手先が要ること、vendored な `fmt` と `pugixml` の MIT 告知、Windows wheel が静的に取り込む mingw-w64 ランタイムの告知である。
別件として、プロジェクトが存在するようになった今、アカウントスコープのトークンはプロジェクトスコープのものに置き換えるべきであり、さらに PyPI の Trusted Publishing へ移行してトークンを一切保管しない形にしたい。
